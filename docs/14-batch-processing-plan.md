# 14 · 原创文字分批处理机制

**建立日期**：2026-10-24
**状态**：机制与清单已建立，**未执行任何模型分析**
**花费**：¥0.00

---

## 一、为什么需要分批

主人不能逐条阅读 223 条原文，也不该被要求挑出「有价值的日记」。

**但同时：**

- 不能因为启发式分数低就永久排除某条原文（Task 07 的候选只取了前 80 条）
- 不能把全部材料压成一份不可追溯的长文本
- 不能重复分析同一条记录

**所以需要一个既能覆盖全部、又能断点续跑、还能追溯每一条的切分方式。**

---

## 二、分批方案

```
主集          223 条（Task 07 的 224 条，按 sha256 去重后 223）
每批          10 条
批次数        23（末批 3 条）
排序          按发布时间升序
时间跨度      2023-07-26 → 2026-10-04
```

### 2.1 为什么是 10 条

| 每批条数 | 优点 | 缺点 |
|---|---|---|
| 1 | 最稳、最可追溯 | 23 批变 223 次调用，开销大 |
| **10** | **单次成本可控，单批产出可读完** | 批内上下文可能互相影响 |
| 50 | 成本最低 | 单次输出过长，质量下降 |

**10 条是经验值。** 如果后续发现批内互相干扰，可降到 5。

### 2.2 批次清单字段

| 字段 | 说明 |
|---|---|
| `batch_id` | `B001` ~ `B023` |
| `batch_seq` | 批内序号 1~10 |
| `record_key` | 脱敏假名（`sha256(salt\|source_id)[:12]`） |
| `month` | 发布年月（精确到月，不公开到秒） |
| `dyn_type` | 动态类型 |
| `len_bucket` | 长度分桶 |
| `processed` | `0` / `1` |
| `needs_review` | `0` / `1` |
| `output_version` | 产出格式版本（当前为空，分析后填 `v1`） |

### 2.3 本地完整版

**公开仓库只有脱敏清单**（`data/text_batch_manifest.csv`）。

**完整版在 `local/text_batch_manifest.csv`**，额外含：

```
record_id      真实动态 ID
pub_iso        秒级时间
pub_ts         epoch
text_source    正文所在字段
sha256_16      内容校验值
raw_path       raw.jsonl 路径
raw_line       raw.jsonl 的行号（1-based）
```

**`raw_line` 是只读定位符**——不复制原文，只记「原文在第几行」。原文永远只有一份。

## 三、断点续跑与增量更新

### 3.1 断点续跑

```
1. 读 local/text_batch_manifest.csv
2. 筛出 processed = 0 的批次
3. 按 batch_id 升序处理
4. 每批完成立即回写该批的 processed / output_version
5. 中断后重跑：已 processed 的批次自动跳过
```

**关键：回写以批次为单位，不以整份文件为重写单位。** 这样即使中途崩溃，已完成的批次不会丢。

### 3.2 增量更新

**新记录出现时：**

```
1. 重新解析 raw.jsonl，取出主集
2. 计算每条 sha256，与已有清单比对
3. 已存在的 sha256 → 跳过（不重复分析）
4. 新增的 sha256 → 追加为新批次（B024, B025...）
5. 已有批次编号不变
```

**同一条记录被不同主题的分析引用时，`source_id` 保持不变，产出另存一份 — 原文来源唯一，分析引用可多份。**

### 3.3 版本

| 版本字段 | 位置 | 含义 |
|---|---|---|
| `schema_version` | `text_analysis_schema.json` | 结构版本 |
| `output_version` | 清单每行 | 该批产出的结构版本 |
| `_template` | 分析结果 | 模板标记 |

**结构变更时，旧产出保留，`output_version` 标记其版本，不覆盖。**

## 四、单条归纳结构

详见 `data/text_analysis_schema.json`，模板见 `data/text_analysis_template.jsonl`。

### 4.1 十个字段

| 字段 | 允许未知 | 说明 |
|---|---|---|
| `source_id` | — | 原始记录 ID |
| `topic` | ✅ | 主要主题 + `basis`（原文说的 / 推断的 / 未知） |
| `emotion_signals` | ✅ | 情绪线索 + `quoted_cues`（支撑判断的原文片段） |
| `salience` | ✅ | 重要程度 + 依据码 |
| `value_tension` | ✅ | 价值冲突的两端 |
| `life_event` | ✅ | 原文明确描述的事件 |
| `interpretation` | ✅ | 暂定解释 + `kind`（复述 / 推断 / 推测） |
| `counterevidence` | 必填 ≥1 | 相反证据或其他解释 |
| `confidence` | — | low / medium / high |
| `review_status` | — | pending / analyzed / needs_review / skipped |

### 4.2 三类信息的分离

**这是 schema 设计的核心。**

```
原文事实      → life_event.described + basis="stated"
作者明确观点  → topic.basis="explicit_in_text" / emotion.basis="explicit"
模型推断      → interpretation.kind="inference" + confidence
```

**任何推断都必须带 `basis` 或 `kind` 标记，不能混在事实里。**

### 4.3 为什么允许 unknown

**任务书要求「情绪归类必须允许未知，不得为了填满字段而猜测」。**

schema 里 `valence` 的默认值就是 `unknown`，`salience.importance` 的默认值也是 `unknown`。

**并且有一条条件校验：如果 `valence = unknown`，则 `basis` 不得为 `explicit`。** —— 防止「声称原文明确说了情绪，但归类为未知」这种自相矛盾。

## 五、降低主人参与成本

### 5.1 默认不打扰

**后续不要求主人逐条阅读原文，也不要求做情绪评分。**

模型处理完后，**只在主人主动要求时**展示结构化总结。

### 5.2 展示时必须带的东西

```
依据的记录数量
支持证据的来源 ID（或脱敏假名）
相反证据
当前的不确定性
```

**没有这四样的总结不展示。**

### 5.3 主人的四种回应

```
确认      → 写入长期记忆
修正      → 记录修正内容，旧结论保留
暂不处理  → 保持 pending，不写入
不查看    → 不展示后续同类总结
```

**「未回应」不等于「默认同意」。** 任何未经确认的结论都停在 `review_status = analyzed`，不进入长期记忆。

### 5.4 禁止

```
✗ 未经授权的心理诊断
✗ 根据少量文字给出确定人格定论
✗ 把推断写成事实
```

## 六、成本估算

**这一节是任务书要求回答的问题：「后续处理全部原文的大致成本如何估算」。**

### 6.1 数据量

```
记录数        223 条
平均长度      约 150 字符
总字符        约 33,000
中文约 1 字符 ≈ 1 token，故输入约 33K token
```

### 6.2 三种方案的成本

**假设单价（DeepSeek 系，公开价目，实际以账单为准）：**

| 项目 | 单价 |
|---|---|
| 输入 | 约 ¥0.5 / 百万 token |
| 输出 | 约 ¥1.5 / 百万 token |

**方案 A：非推理模型，一次全量**

```
输入   33K × ¥0.5/M  = ¥0.017
输出   223 条 × 约 150 token = 33K × ¥1.5/M = ¥0.050
────────────────────────────────────
合计   约 ¥0.07
```

**方案 B：推理模型（如 deepseek-flash），一次全量**

```
输入   33K × ¥0.5/M  = ¥0.017
输出   223 条 × 约 600 token（含推理链）= 134K × ¥1.5/M = ¥0.20
────────────────────────────────────
合计   约 ¥0.22
```

**方案 C：分 23 批，每批单独调用（含 prompt 开销）**

```
输入   33K + 23 × 500（系统提示词重复）≈ 44K × ¥0.5/M = ¥0.022
输出   134K × ¥1.5/M = ¥0.20
────────────────────────────────────
合计   约 ¥0.22（与 B 接近，略高）
```

### 6.3 结论

**¥7 余额足够把全部 223 条跑 30 遍以上（方案 A）或 30 遍（方案 B/C）。**

**真正的限制不是钱，是：**

1. **质量**——一次跑完 223 条，单条质量必然下降
2. **复核**——产出后仍需要人判断，那个成本比 token 贵得多
3. **授权**——任务书要求「先报告成本、等待主人单独授权」

**建议：先试跑一批（B001，10 条，约 ¥0.01），看产出质量再决定是否全量。**
